# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-11-21 | Reuse closed PRs #1–#4 (refs/pull/N/head, based on f92cd08), split into smaller releases | They already fix most findings and are tested; they were too big to review and predated the studio baseline |
| 2026-11-21 | The production `PASS_PHRASE` lives only in `local.properties` (git-ignored). Agents never read that file | It is the legacy key for every existing user's vault |
| 2026-11-21 | Free, no ads, no paywall | Trust is the product; "no ads" is the top praise in 5★ reviews |
| 2026-11-21 | Keep the "PassKey" brand; change the Play title to a keyword-led one; move to Productivity | Keeps 34K installs and existing ratings; the brand alone loses to the "passkeys" term |
| 2026-11-21 | Keep Firebase Analytics and Crashlytics, but consent-gated, no ad ID, no PII, no vault content; the listing says "vault never leaves your phone", not "no internet" | Owner wants analytics; honesty in the Data-safety form and the listing |
| 2026-11-21 | Rejected: HIBP breach check and WorkManager auto-backup. Approved: backup-reminder notification and Credential Manager provider | Owner decision on opt-in features |
| 2026-11-21 | Passkey (FIDO) storage planned for 6.1.0 | Makes the name match what searchers expect; answers the "passkeys not working" reviews |
| 2026-11-22 | 5.5.2 keeps `allowBackup="true"`; it is turned off in 5.6.0 together with the encrypted backup | Turning it off first would remove the only automatic way to move the vault to a new phone before a safe replacement exists. Android cloud backup is end-to-end encrypted by the screen lock on API 28+ |
| 2026-11-22 | Third onboarding page no longer promises autofill (it returns in 5.8.0 when autofill ships) | The feature didn't exist; an honest release can't advertise it |
| 2026-11-22 | Consent: two switches (crash+performance, usage statistics), both off until chosen, "Decline all" and "Allow all" with equal weight; upgrading users are asked once, before unlock | Opt-in without dark patterns; matches the studio baseline consent model |
| 2026-11-22 | Performance Monitoring follows the crash/diagnostics choice. Crash reports captured before the choice are kept on the device: sent if the user allows, deleted on an explicit decline (owner chose this over deleting while undecided) | First-run crashes (onboarding, consent screen) would otherwise be invisible; a "no" still guarantees they are never sent |
| 2026-11-22 | Firebase automatic screen reporting off; `screen_view` comes only from navigation | Avoids duplicate per-Activity screen views; route names only |
| 2026-11-22 | The password keyboard on the Response field becomes a per-field choice in 5.6.0 (with `isSecret`) | Owner decision: keyboards hide Enter and suggestions for multi-line notes and usernames |
| 2026-11-22 | AD_ID and AdServices permissions removed with `tools:node="remove"`; ad-ID collection off | No ads, so no reason for an advertising ID in a password manager |
| 2026-11-22 | ktlint package-name and filename rules, and detekt PackageNaming, disabled until Phase 4a | Renaming packages now would break cherry-picking archived PR #4 |
| 2026-11-22 | detekt runs as detekt-cli 1.23.8 via a JavaExec task; 16 pre-existing findings baselined | The 1.23 Gradle plugin doesn't support Kotlin 2.x; new code must stay clean |
| 2026-11-22 | New and legal strings are machine translations into 16 locales, pending native review | `MissingTranslation` is a build error; shipping English legal text to 16 locales was the bug being fixed |
| 2026-11-22 | Local JVM builds use Corretto 22 (`JAVA_HOME`); Gradle 8.14 cannot run on Android Studio's bundled JDK 25 | Toolchain upgrade comes in 5.6.0 |
| 2026-11-22 | Studio baseline dependencies: firebase-config (Firebase BOM 34.19.0), kotlinx-coroutines-play-services 1.11.0, com.google.android.play:review 2.0.2 (not review-ktx, which breaks R8) | Mandatory baseline (Remote Config, force update, banner, In-App Review); versions verified on Maven |
| 2026-11-22 | Baseline launch order not adopted wholesale: PassKey keeps its tested onboarding → consent → unlock router; update and maintenance gates are overlays (UpdateHost) | Template README allows keeping an app's tested order; a hard update must block even the lock screen |
| 2026-11-22 | Soft update prompts only on the unlocked vault home; never during onboarding, unlock or editing | Studio ads/prompt philosophy: never mid-flow |
| 2026-11-22 | Remote Config fetch disclosed in Privacy (installation identifier, no vault content); it is not consent-gated because it carries no usage data and is needed for force update / maintenance | Honest Data-safety answer; safety-critical kill switch must work for everyone |
| 2026-11-22 | Privacy/Terms/About are full screens (Legal/About template); the Settings BottomSheetScaffold is gone | The scaffold sheet caused the monkey crash (seed 5521); screens scroll, have back buttons and work with TalkBack |
| 2026-11-22 | Default support_email and privacy_url point at the public repo's Privacy Policy and the email already published there; terms are in-app only (terms_url empty) | Values already public; RC can change them without a release |
| 2026-11-23 | Remote Config `maintenance_mode` is ignored in PassKey (`withoutMaintenance`); forced updates still apply | Owner choice (finding #2): an offline vault has no server to maintain, and a cached "on" could lock people out of their own passwords |
| 2026-11-23 | Announcement CTAs may only open an allowlist of screens (Settings, About, Terms, Privacy, Privacy options) | Owner choice (finding #1): an unknown route crashed NavController; vault screens must never open from a remote string |
| 2026-11-23 | 5.7.0 recovery-password slot uses PBKDF2-HMAC-SHA512 (as the backups do), not Argon2id via argon2kt | Owner choice: no native third-party dependency in the key path; strong with a decent password |
| 2026-11-23 | Recovery password is mandatory, set once (new installs during setup; existing users on first launch of 5.7.0, before the re-key) | Owner choice: removing the screen lock destroys every Keystore key; without it the vault could be lost for good. Doubles as the master password reviewers asked for |
| 2026-11-23 | detekt complexity/return-count/generic-catch suppressed (with reasons) on VaultMigration.runMigration and DatabaseKeyManager.tryCredentialSlot | The re-key is a deliberately linear sequence whose order is the safety argument; restructuring it for style adds risk to the riskiest code path. Covered by on-device VaultMigrationTest |
| 2026-11-23 | PR #3's VaultMigrationTest and KeyStoreWrapperTest are opt-in (`-e destructiveVaultTests true`), including their @After cleanup | They delete the app's real vault database and Keystore keys; a normal connected-test run must never destroy a device's vault |
| 2026-11-23 | LaunchFlowE2ETest is opt-in (`-e launchFlow true`) from 5.7.0; the activity rule closes best-effort | The flow now ends at real system authentication that only host scripts can answer; a prompt left up hung the runner |
| 2026-11-23 | Recovery password needs 10+ characters and must not rate "weak" (repeats, runs like 123456, common words, low variety); a text-plus-bar strength meter is shown. Backup passwords keep the 8-character rule | Owner choice (5.7.0 finding #1): the REC slot can be guessed offline by anyone with the phone's files, so its strength is the real protection. Counted in code points so non-Latin passphrases are fair |
| 2026-11-23 | 5.7.0 upgrade funnel events: recovery_setup_shown/completed (`existing_vault`) and vault_migration_failed (`reason` enum only) | Owner choice (5.7.0 finding #2): the staged rollout needs a signal; no vault content or password data is sent |
| 2026-11-23 | 5.7.0 goes straight to a 100% rollout (owner decision, replacing the 5% → 20% → 100% plan) | Owner choice; the Remote Config min-version kill switch and vault_migration_failed are the safety net. The rollout itself is set by the owner in Play Console |
| 2026-11-23 | Physical-device checks use the owner's Moto G34 | Owner choice; needs USB debugging. Release-signed Play builds cannot be replaced by a debug build without uninstalling (which wipes data), so the upgrade check goes through a Play testing track |
| 2026-11-23 | 5.8.0 phase 4a: PR #4's navigation and MVI commits were rebuilt on the current tree instead of cherry-picked | They predate the 5.6.0 lock guard, announcement allowlist, Undo and in-sheet errors; a blind pick would have regressed them. Layering and domain-model commits were picked and resolved |
| 2026-11-23 | Type-safe routes: Remote Config announcements keep their existing strings, mapped to NavRoute through the allowlist; screen_view keeps the old screen names | No console or dashboard change; a remote value is never parsed into a route |
| 2026-11-23 | detekt TooManyFunctions ignores overridden functions | A repository implementation is already counted through its interface (threshold 25) |
| 2026-11-23 | Settings analysis runs on an injected @WorkDispatcher (Dispatchers.Default) | Testable without real threads; same behaviour as Dispatchers.IO before, on the right pool for CPU work |
| 2026-11-23 | Autofill matching: web pages by registrable name + full host, apps by publisher label (only when no page address), headings by whole word | PR #4 matched substrings both ways, so com.fakegoogle.login and google.evil.com were offered Google logins. Trade-off: an entry named "Gmail" no longer matches the Gmail app (com.google…); "Google" does. A URL field (6.0.0 templates) will allow exact matching |
| 2026-11-23 | Removing an authenticator needs confirmation | Losing a TOTP secret can lock the user out of the account; PR #4 deleted on one tap |
| 2026-11-23 | Robolectric not added (PR #4 used it for one backup test) | Outside the stack; BackupCodecTest and the simulation cover the same round trip without a ContentResolver |
| 2026-11-23 | A test-only login form (androidTest AutofillTargetActivity) for on-device autofill checks | The emulators have no browser or app with a login screen; never shipped in the app APK |
